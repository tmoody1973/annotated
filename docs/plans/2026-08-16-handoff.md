## What happened today

Tarik published two clips from one YouTube video through the store build. The
first failed permanently; the second worked. That surfaced three defects and one
missing feature, all now fixed and deployed.

### 1. A clip failed and could never be rebuilt

The landing page told the author to "try clipping it again", which meant going
back to the extension and publishing a **second annotation at a different URL**.
The original stayed broken forever and anyone already holding the link kept
seeing the failure.

**`clips.retrySlice`** re-slices the same row — same URL, same votes, same
comments. Author-only, and only on a row that actually failed. There is a **Try
again** button on the failure notice, visible only to the author.

Ownership is answered by **`clips.canRetry`** rather than by exposing the
annotation's `authorId` to every client for the UI to compare. An annotation can
be published anonymously; shipping its author so a button could render would
undo that. Same pattern is used again in `annotations.ownerActions`.

`ClipMediaLive` now also subscribes while `mediaState === "failed"`, not only
while processing. Without that, a retried clip sat showing the failure until a
manual reload — the reload that whole live path exists to avoid.

### 2. The pipeline never retried anything

One transient worker error went straight to `markFailed`. It now attempts three
times with backoff, **skipping the retry on a timeout**: a timeout means the
download was still running, so retrying restarts the same slow work and is
likelier to exhaust the action than to succeed.

### 3. The actual cause, which was not transient

I initially diagnosed this as a blip and **that was wrong** — worth knowing so
the mistake is not repeated. The `200` I saw 37 seconds after the `502` was the
*second clip at a different timestamp*, not a retry of the first.

The real finding:

| span | length | result |
|---|---|---|
| 2:00 → 3:00 | 60s | failed, three times in a row |
| 10:37 → 11:37 | 60s | ready |

Same video (`kX1Sd17KbLY`), same length, different position. yt-dlp's
`--download-sections` hands the cut to its own ffmpeg pass, and that pass fails
on some videos depending **where** the span starts, with a bare
`ERROR: ffmpeg exited with code 1`.

The worker now falls back to `--force-keyframes-at-cuts` after the fast path
fails. That flag was removed in June for speed (it was ~85% of a slice's time)
and must stay off by default; as a *second* attempt it costs nothing on the
videos that already work. **Verified:** the clip that failed three times is now
`ready` and serves 2,883,305 bytes of mp4.

### 4. Users could not manage anything they published

No delete, no edit, no comment removal, no soft-delete field. The ••• menu was
share options only. The June conceptual-model audit locked "Published →
Removed" semantics and they had never been built.

Now built, with the reasoning that decided each:

- **Removal is soft.** A clip page is a receipt someone else can cite, so a hard
  delete turns every pasted link into a 404 and quietly rewrites what other
  people saw. The row stays and resolves to a tombstone; every listing hides it.
- **The listing filters are load-bearing.** One `isVisible` predicate, called in
  all six places that list annotations: feed, Editor's Picks, profile, topic
  room, thread page, and the "N clips" badge — which was otherwise happy to
  count clips it would not render. **If you add a new listing query, filter it.**
- **Editing a take closes the moment anyone engages.** Rewriting after votes or
  replies changes what people endorsed. But "I'm not sure I like like" is a real
  typo in a real published clip, so the take stays editable until the first vote
  or comment, then never again.
- **A removed note keeps its place** so replies still make sense, but its text is
  dropped server-side rather than hidden by the client, and `commentCount`
  follows so "N notes" matches what a reader can see.

succeeding** — check the site rather than trusting the exit.

### Known gaps, deliberately not built

- **No moderation for removal.** Only the author can remove their own work.
  There is no admin path and no way to remove someone else's.
- **No undo on removal.** `removedAt` is set and the clip blob is deleted, so
  restoring would need a re-slice. The mutation is idempotent but not reversible.
- **The tombstone page is not styled.** `toLandingView` now returns `removed:
  true` and `canEditTake`, but the landing page does not yet render a distinct
  removed state — it will just show the take with no media. Worth finishing.
- **`OwnerActions` is only on the landing page**, not on feed cards. The ••• menu
  still only offers share options.
- **Podcast clips are much faster than YouTube.** Podcast slices cut from a
  frozen episode already in Convex storage (ffmpeg range-seek, seconds).
  YouTube fights a ~30KB/s download throttle, so a 90-second clip is ~2 minutes.
  The hero path is the fast one; the path everyone else leads with is the slow
  one. Nothing in the product says so.

## Landmines

- **`convex deploy` is not the deploy command.** `npx convex dev --once` pushes
  functions to `strong-eel-665`, which is what the site reads despite being
  labelled "dev". The "prod" deployment (`colorful-beagle-118`) is empty.
- **Two extension zips.** The store rejects a manifest containing `key`; the
  sideload build needs it for a stable id registered in Clerk. `package:store`
  strips it. Uploading the wrong one fails at the last step of a submission.
- **The store rejects a re-upload that reuses a version number.** Bump
  `apps/extension/package.json` *and* `apps/web/content/changelog.ts` in the same
  commit — they have drifted apart twice now within a day of being aligned.
- **yt-dlp goes stale silently.** The Dockerfile pulls `latest` at *build* time,
  so it freezes at the last worker deploy. On 2026-08-12 a five-month-old build
  returned only storyboards for one video while working on others. If YouTube
  clipping starts failing, redeploy the worker first.
- **`fly ssh console -C` stopped returning stdout** during this session after
  working earlier. Diagnostics that rely on it may silently produce nothing —
  write to a file and `cat` it in a second call, or use the worker's HTTP API.
